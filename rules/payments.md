# Rule: Money Safety

**Status:** Active · **Since:** 2026-07-25 · **Enforcement:** Convention (blocking at review)

## Why this rule exists

This app moves real money between a customer's bank and a merchant's account. A defect here
does not produce a wrong screen — it produces a wrong ledger, a charged customer with no
receipt, or a payment that can be claimed by someone who never paid.

Every requirement below exists because a specific attack or failure was worked through and
found to break something. The teaching version, with the scenarios behind each rule, is in
[`implementation-gate.md`](implementation-gate.md).
This file is the enforceable version.

**A code path "touches money" if it can create, change, or cancel a Payment Entry, or if it
calls a Paymob refund endpoint.** Every requirement applies to all
such paths, whether written by a human or generated by an AI.

## The requirements

### Writing to the ledger

1. **One write path.** Exactly one function creates Payment Entries. The webhook handler, the
   reconciliation poller, and any manual action all call it. No second path.
2. **The API response is never the truth.** A Payment Entry is created from a verified webhook
or from a Transaction Inquiry result — never from the HTTP response of a refund
   call. A lost response and a failed request are indistinguishable.
3. **Status is derived.** The Payment Request status comes from submitted Payment Entries and
   their allocations. It is never written by hand.
4. **Every Payment Entry is allocated** to the specific Sales Invoice through the `references`
   table. An unallocated entry leaves the invoice overdue while the cash floats unapplied.

### Trusting the message

5. **Verify first.** HMAC-SHA512 verification runs before loading documents, reading amounts,
   or touching the database. Comparison uses `hmac.compare_digest`, never `==`.
6. **A valid signature is not permission to post.** Authenticity, success state, and amount
   match are three separate checks. All three must pass.
7. **Amount mismatch never posts.** An authentic callback whose amount differs from the
   expected amount creates an audit record and posts nothing. A human decides.

### Amounts

8. **Money is integer cents.** The expected amount is stored as an integer field at intention
   time and compared directly against `amount_cents`. No float arithmetic, no float equality.
9. **Never exceed the verified charge.** A refund is checked against the verified charged amount
   read from Paymob data — never from a browser-supplied parameter.

### Doing things twice

10. **Incoming duplicates are deduplicated.** A unique database constraint on the Paymob
    transaction ID. A repeated webhook returns HTTP 200 and changes nothing.
11. **A second genuine payment for the same Payment Request is caught separately.** Different
    transaction IDs pass rule 10. Check whether a submitted Payment Entry already exists for
    the Payment Request; if so, audit it and flag it for a human refund — the customer was
    really charged twice.
12. **Outgoing duplicates are locked, not deduplicated.** Refunds take a
    server-side lock on the Payment Request before the API call. A disabled button is not a
    defense, and neither is trusting Paymob to reject the second request.
13. **Retry reads, never retry writes.** Transaction Inquiry may be retried automatically.
    Refunds may not — Paymob's endpoint takes no idempotency key, so a retry
    is a new money movement. Re-issuing is a human decision.

### Failing safely

14. **Errors never change payment state.** A 401, timeout, or 5xx means "try again later". Only
    an answer from Paymob changes state. Auth-token expiry means refresh and retry, keeping the
    payment pending; it is not the same as intention expiry, which is terminal.
15. **Failed payments touch nothing else.** A decline updates the Payment Request status only.
    No ledger row, no change to the Sales Invoice, and the customer can still start a new
    attempt with new intention identifiers.
16. **Every outbound call sets a timeout** and handles connection errors explicitly.

### Who may act

17. **Every `@frappe.whitelist()` is a public endpoint.** Every money-moving method checks
    permission on the document before doing anything. `allow_guest=True` on a money-moving
    method is an automatic reject.
18. **Browser input is attacker-controlled.** Amounts and references are read from the database
    or from verified Paymob data, never taken from the request body as authoritative.

## Definition of Done

A slice that touches money is not done until every box is true:

- [ ] All ledger writes go through the single shared function.
- [ ] No Payment Entry is created from an API response.
- [ ] Signature verified before any other logic; `compare_digest` used.
- [ ] Amounts compared as integer cents against the stored expected amount.
- [ ] Duplicate incoming messages provably ignored (unique constraint, not an `if`).
- [ ] Outbound money calls take a lock before the request.
- [ ] Every whitelisted money method checks permission first.
- [ ] Every outbound call has a timeout and explicit error handling.
- [ ] Failure paths leave the ledger and the Sales Invoice untouched.

## What this rule is NOT

- Not a substitute for reading the code. The checklist finds known mistakes, not new ones.
- Not applicable to read-only reporting or display code — but "it only displays" must be true,
  not assumed.
